Block မှာတော့ ကျနော်တို့က Defense ကောင်းချင်ရင် Offense ကောင်းရမယ်လို့ ယုံတယ်ဗျ။ အထူးသဖြင့် AI System Security ပိုင်းမှာပေါ့။ ဒါကြောင့် General-purpose Open Source AI Agent ဖြစ်တဲ့ goose ကို Release လုပ်တုန်းက Attacker တွေ ဒါကို ဘယ်လို Abuse လုပ်နိုင်မလဲဆိုတာ ကြိုသိထားဖို့ လိုလာတယ်။
Operation Pale Fire ဆိုတာကတော့ ကျနော်တို့ Internal Red Team ရဲ့ Project တစ်ခုပါ။ အဓိက မေးခွန်းကတော့ "Attacker တွေက goose ကိုသုံးပြီး Block Employee တွေကို ဘယ်နည်းလမ်းတွေနဲ့ Compromise(ထိန်းချုပ်) လုပ်နိုင်မလဲ?" ဆိုတာပါပဲ။
ရလာတဲ့ Result တွေက goose ရဲ့ Security Posture ကို မြှင့်တင်ဖို့ တော်တော်လေး အထောက်အကူပြုတယ်။ ကျနော်တို့ရဲ့ Offensive Security Team က Invisible Unicode Character တွေကြားထဲ Prompt Injection ဝှက်ပြီး Employee Laptop တစ်လုံးကို Compromise(ထိန်းချုပ်) လုပ်နိုင်ခဲ့တယ်။ Detection and Response Team (DART) ကလည်း ဒီ Threat ကို ချက်ချင်း Identify လုပ်ပြီး Contain လုပ်နိုင်ခဲ့တော့ Detection Coverage နဲ့ Incident Response Process တွေ ပိုမို တောင့်တင်းသွားတာပေါ့။

Background: What is goose?
Block (အခုတော့ Agentic AI Foundation - AAIF အောက်ရောက်သွားပြီ) က develop လုပ်ထားတဲ့ goose ဟာ Open Source AI Agent တစ်ခုပါ။ Coding task တွေ၊ Debugging နဲ့ Workflow Automation တွေလုပ်ဖို့ User တွေကို ကူညီပေးတယ်။ goose က Model Context Protocol (MCP) extension တွေကနေတဆင့် External entity တွေနဲ့ ချိတ်ဆက်ပြီး Complex multi-step operation တွေ လုပ်နိုင်စွမ်းရှိတယ်။

The First Campaign

What Went Wrong?
အလွဲတွေကတော့ အများကြီးပဲ။ Model တွေရော goose agent ရောက Rapid pace နဲ့ ပြောင်းလဲနေတာကိုး။ goose မှာက Internal user တွေအနေနဲ့ Vendor မျိုးစုံက Model တွေကို စိတ်ကြိုက်ရွေးသုံးခွင့် ပေးထားတယ်။ ပြဿနာက Model တစ်ခုအတွက် Tune ထားတဲ့ Payload က နောက် Model တစ်ခုမှာ အလုပ်မဖြစ်တာမျိုး ရှိတတ်တယ်။ LLM တွေက Non-deterministic ဖြစ်တော့ ကျနော်တို့ရဲ့ "Update" instruction ကို မ run တာမျိုးလည်း ဖြစ်နိုင်တယ်။ နောက်ပြီး User တွေရဲ့ Context window ထဲမှာ သူတို့ Enable ထားတဲ့ Tool တွေ၊ Calendar အခြေအနေတွေအလိုက် Content တွေက ကွာခြားနေနိုင်တယ်။
အဲဒီအချိန်မှာပဲ Google Calendar MCP က Update အကြီးကြီးတစ်ခု ထွက်လာပြီး Attack efficacy ကို တော်တော်လေး ထိခိုက်သွားစေတယ်။ Tool က Date range အလွဲတွေ ယူမိပြီး Injection ကို ကျော်သွားတာမျိုး ခဏခဏ ဖြစ်လာတယ်။
User (သို့) Agent prompt ကနေ Injection လုပ်တာက Technically possible ဖြစ်ပေမယ့် Consistent မဖြစ်ဘူးဆိုတာ သဘောပေါက်လိုက်တယ်။ ဒါနဲ့ System prompt ကို တိုက်ရိုက် Target ထားတဲ့နည်းလမ်းကို ပြောင်းသုံးဖို့ ဆုံးဖြတ်လိုက်တယ်။ ဒါက Model version, MCP နဲ့ goose version မတူရင်တောင် ပိုပြီး Consistent ဖြစ်မယ့် နည်းလမ်းလေ။

The Actual Attack
goose Shareable Recipes

The Second Campaign
Shared recipe technique ကိုသုံးပြီး Calendar invite description ထဲမှာ Recipe URL ထည့်လိုက်တယ်။ Recipe ထဲမှာလည်း ASCII smuggling technique ကိုပဲ ပြန်သုံးထားတော့ Curious user တစ်ယောက်က Base64 decode လုပ်ကြည့်ရင်တောင် Hidden instruction တွေကို မြင်ရမှာ မဟုတ်ဘူး။ Google Calendar rate limit ကြောင့် တစ်ရက်ကို ၅၀ နှုန်းနဲ့ပဲ Second round စ လိုက်တယ်။
Invite ထဲမှာ Google Meet link ပါတော့ ပိုပြီး Legit ဖြစ်မယ်လို့ မျှော်လင့်ထားတယ်။ Meeting အချိန်ရောက်တော့ Slide deck ဖွင့်၊ Internal learning session လိုလို ဘာလိုလိုနဲ့ Demo ပြရင်း Poisoned recipe ကို run ခိုင်းလိုက်တယ်။ Server မှာ Request တွေ ဝင်လာတာ တွေ့လိုက်တော့ "မိပြီဟေ့" လို့ ထင်လိုက်တာ။
Payload execute ဖြစ်မဖြစ် စောင့်ကြည့်နေပေမယ့်... ဘာမှ ဆက်မဖြစ်လာဘူး။ ဘာဖြစ်သွားတာလဲ?
